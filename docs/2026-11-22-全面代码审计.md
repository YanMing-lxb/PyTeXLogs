## 1. 确定性缺陷（附复现与影响）

### B1（P1）严重度过滤后统计字段残留旧值

**位置**：`src/pytexlogs/exporters/json_exporter.py:244-251`，同类问题在 `cli/main.py:271-274`

`_filter_report_result` 只重算：

```python
stats["entries_count"] = len(kept)
stats["error"] = sum(...)
stats["warning"] = sum(...)
```

`typesetting`、`overfull_boxes`、`underfull_boxes`、`undefined_references` 等键仍保留过滤前的值。复现：过滤前 `stats` 含 `typesetting:1, overfull_boxes:1, entries_count:2`；按 `ERROR` 过滤后 `entries` 只剩 1 条 error，`entries_count` 变 1，但 `typesetting:1, overfull_boxes:1` 仍在。CLI 的 `--severity` JSON/CSV/SARIF 导出会带上这份矛盾统计；`_filter_against_baseline` 也只改 `entries_count/error/warning`，baseline 过滤同样失真。

**影响**：消费者按 stats 做门禁或看板时得到错误数字；这是契约字段，不属于纯展示问题。

**修复方向**：把统计重算收敛为一个函数，覆盖 `levels`、各等级计数、`overfull/underfull/undefined`、`entries_count`，所有过滤路径共用；补 stats 断言测试，不能只断言 entries。

### B2（P1）参考文献摘要块行数错位导致崩溃 / 静默丢行

**位置**：`src/pytexlogs/display/printer.py:237-275`

`added_block_markup` 用 `_format_ref_block` 生成，`added_block_plain` 用 `_wrap_key_block` 独立生成，然后：

```python
for i, line in enumerate(added_block_markup):
    emit(line, added_block_plain[i])
```

两套算法换行结果经常不一致。随机 fuzz 中，键长 `[20,120,20]` 得到 markup 3 行、plain 4 行；键长 `[21,5,41,121]` 得到 markup 4 行、plain 3 行。前者在 `ref_removed_keys` 场景下 `added_block_plain[i]` 越界。

端到端复现：

```python
print_summary(
    [ParsedLog()], use_logger=False,
    ref_added_keys=["k"*21, "k"*5, "k"*41, "k"*121],
    ref_total=4, stream=io.StringIO(),
)
# IndexError: list index out of range
```

`run_pipeline` 调用 `print_summary` 未包 try，长 cite key（约 >112 字符）可让 CLI 直接失败；行数相反时则静默丢掉日志里的部分参考文献行。该段无测试，`display/formatter.py` 覆盖率 54%、`display/printer.py` 64%。

**修复方向**：只保留一套换行算法，plain 由 markup 逐行 `_strip_rich_markup` 得到（与 top-cited 块一致），从结构上消除索引配对；补长键、空键、多行中文键的测试。

### B3（P1）单文件 `.blg` 自动选错解析器，Biber 日志静默 0 条

**位置**：`src/pytexlogs/easy.py:57-69`、`easy.py:86`

`.blg` 同时注册给 BibTeX 与 Biber，两者 importance 都是 `high`，`sorted` 稳定排序后先注册的 BibTeX 胜出。用真实 fixture `tests/fixtures/real_miktex/biber_case_mismatch.blg`：

- `parse_log_file(path)` → `tool=bibtex, entries=0`
- `parse_log_file(path, engine="biber")` → 2 条 WARN

即 `pytexlogs check main.blg` 对 Biber 日志静默显示 0 条问题。`.glg` 同理，Xindy 先注册，`makeglossaries` 生成的 `.glg` 会被 Xindy 解析器接管。docstring 已承认“`.blg` 有歧义，默认取 bibtex”，但默认行为对 Biber 用户是错误结果。

**修复方向**：`.blg` 先做内容嗅探（Biber 日志有 `INFO - This is Biber` / `WARN -` 等特征），无法判定时才按后缀回退；`.glg` 同样嗅探 `makeglossaries`/`xindy` 头。补真实 fixture 测试。

### B4（P1）规划步骤与实际发现路径不一致，`plot.asy` 永不解析

**位置**：`src/pytexlogs/core/logkind.py:127-130`；`core/registry.py:37-43`、`registry.py:162-168`

规划用 `any(aux.glob("*.asy"))` / `any(aux.glob("*.pygmented"))` 决定加入 asymptote/minted，但 `default_discover` 只找 `${jobname}.asy`。复现目录：`main.log + plot.asy + other.pygmented`：

- `plan_default_steps()` 返回 `['pdflatex', 'asymptote', 'minted']`
- asymptote 实际 discover 到 **`main.log`（LaTeX 日志）**
- minted discover 为 `None`
- 最终 `skipped_steps=['asymptote','minted']`，`plot.asy` 永远不被解析

更危险的是自定义 steps 顺序：若把 `asymptote` 放在 `pdflatex` 前，`AsymptoteParser` 会消费 `main.log`，LaTeX 步骤被标记为 skipped，等于顶掉主日志。根因是 asymptote spec 把 `.log` 也列为后缀（`registry.py:164`）。

**修复方向**：asymptote 去掉 `.log` 后缀；规划与发现使用同一规则（要么都按 jobname，要么都 glob 并返回具体文件列表）；引擎消费路径时对“多候选”显式排序，不能只接受单个 Path。

### B5（P2）Biber 解析器实例复用返回陈旧路径

**位置**：`src/pytexlogs/parsers/biber.py:51`、`biber.py:54-83`

`_resolved_paths` 在 `parse()` 中不清空；`bibtex.py:93` 有 `clear()`，Biber 没有。复现：同一实例先以 `A/main.tex` 解析，再以 `B/other.tex` 解析同一个 `refs.bib`，第二次仍返回 `A/refs.bib`。CLI 每次新建实例，所以主要影响库用户和未来的批量复用。

**修复方向**：`parse()` 开头 `self._resolved_paths.clear()`，与 BibTeX 对齐；补实例复用测试。

### B7（P2）CLI logging 配置接错 logger 且重复添加 handler

守卫检查 `logging.getLogger("pytexlogs").handlers`，handler 却加到 `logger = getLogger("pytexlogs.cli")`，并设置 `propagate=False`。复现连续调用 `main(["--version"])` 3 次：

### B8（P2）Windows 下 `--open` 丢失行号跳转

**位置**：`src/pytexlogs/cli/args.py:58-69`、`args.py:84-88`

只识别 `basename in {"code", "code.exe"}`；本机 `shutil.which("code")` 返回 `C:\Applications\Scoop\apps\vscode\current\bin\code.CMD`，因此走 else，只追加文件、不追加 `--goto file:line`。同类问题：`_detect_editor("code --wait")` 返回单 token `["code --wait"]`（未 `shlex_split`），`Popen` 会当成不存在的可执行文件名。

**修复方向**：接受 `code.cmd`/`code.bat`（大小写不敏感），命令串先 `shlex.split(posix=...)`；补 Windows 路径测试。

### B9（P2）注册表元数据与 parser 自报元数据漂移（4 项）

**位置**：`core/registry.py:148-175` 与各 parser 返回值

逐 step 对比空输入解析结果：

| step | registry spec | parser 自报 | 影响 |
|---|---|---|---|
| `asy`/`asymptote` | `external/low` | `graphics/medium` | 单文件与 pipeline 分类/优先级不同 |
| `minted` | `code/low` | `code/medium` | 同上 |
| `nomencl` | `glossary/medium` | `glossary/low` | 同上 |
| `pythontex` | `code/low` | `code/high` | 同上 |

`tests/test_log_parsers.py:22-23,43-44,68-69` 还把单文件口径（pythontex high、asy medium）写死。`display/formatter.py:165` 再把未知 category（`external`/`custom`）静默折叠进 `compile`，pipeline 报告的 Asymptote 条目在文本摘要里显示成“一般编译”；`CATEGORY_ORDER/CATEGORY_LABEL`（`formatter.py:80-96`）没有 external/custom。

**修复方向**：确定单一事实源（建议 registry spec 权威，parser 只负责解析）；单文件 API 也从 registry 取元数据；`CATEGORY_ORDER` 增加 external/custom 或显式降级并记录 warning。此项是行为/契约变更，需先补测试再改。

### B10（P2）BibTeX 裸 `---while reading file` 生成空文本 ERROR

**位置**：`src/pytexlogs/parsers/bibtex.py:181-183`

对空前缀不做保护。复现 `---while reading file refs.aux` → `('error', '…refs.tex', 1, '')`。空 message 会污染 JSON/CSV/SARIF，并让去重键退化为“同文件同行同级别”的碰撞。

**修复方向**：空前缀时保留原始行文本或跳过；补畸形输入测试。

### B11（P2）`run_demo` 重复计算摘要且手写摘要为空

**位置**：`src/pytexlogs/integration_demo.py:53-78`

`run_pipeline` 未传 `print_terminal=False`（引擎默认 True），随后又把 `ToolResultReport.entries`（`level` 为字符串）直接塞进 `ParsedLog` 再 `print_summary`。`_group_by` 用枚举比较字符串，必然不匹配。实际 `pytexlogs demo` 只显示引擎打印的一份正确摘要，手动那份为空，属于空转代码。

**修复方向**：`run_pipeline(..., print_terminal=False)`，并直接把 `ParsedPipelineReport` 交给 `print_report`/统一渲染入口，不要手工重建 `ParsedLog`。

### B13（P2）LaTeX 专用告警分支大面积不可达

**位置**：`src/pytexlogs/parsers/latex.py:86`、`latex.py:123-153`、`latex.py:579-730`

`latex_warn_re` 已先匹配 `Class/Package/Module/LaTeX/LaTeX3` 告警；其后的：

**修复方向**：调整匹配顺序（专用正则先于通用 `latex_warn_re`），或删除不可达分支；无论哪种都要用现有 fixtures 做输出等价/差异对比。

### B14（P2）`manager.run` 与 `run_pipeline` 行为不一致

**位置**：`core/manager.py:100-156`；`core/engine.py:214-278`

- `manager.run` 直接 `parser.parse_file(log_path)`（136 行），parser 抛异常会中断整个 `parse_auxdir`；`run_pipeline` 捕获异常并继续（`engine.py:253-257`）
- `manager.run` 不传 `root_file`，engine 传
- manager 用 `parse_file` 二次读盘，engine 先 `_read_log_text` 再 `parse`
- `manager.py:144-147` 的 `spec is None` else 分支不可达（`_resolve_parser` 已保证 parser 与 spec 同时存在）

**影响**：用户从 `parse_auxdir` 切到 `run_pipeline` 会看到不同成败语义；一个损坏的 `.log` 可以让便捷 API 整体失败。

**修复方向**：让 manager 复用 engine 的单步执行函数，或把 engine 的异常策略下沉到 manager；删除不可达分支。属于行为变更，需先统一契约。

### B15（P3）并发写状态/报告的竞态

- `core/state.py:168-171`：`clear()` 先 `remove_namespace`（持锁），再在锁外 `_prune_if_empty()`；另一进程若在间隙写入新命名空间，可能被 `unlink` 连带删除。
- `core/report.py:95`：固定 `path.with_suffix(path.suffix + ".tmp")`，两个进程写同一报告会争用同一临时文件，后写者可能覆盖/截断前者。

**修复方向**：`_prune_if_empty` 在同一个锁内完成读-判-删；临时文件用 `tempfile.NamedTemporaryFile(dir=path.parent)` 或带 pid/uuid 后缀。

## 3. 冗余与重复实现

### 3.1 两套流水线

- `core/engine.py:214-278` 完整重写了 `core/manager.py:100-156` 的 step 循环。
- engine 只为拿 `manager.registry`，却复制了发现、消费路径、解析、结果装配的全部逻辑。
- 差异：异常策略、`root_file` 传递、`parse_file` vs 文本解析。
- 维护风险：任何 step 语义修改都要改两处，且已有行为分叉（B14）。

**建议**：抽 `_run_step(spec, log_path, root_file)` 单一实现；manager 作为轻量包装，engine 负责编排与报告。

### 3.2 索引/术语表解析三份复制

- `miktex_style_error_re` + brief 正则：`makeindex.py:25-26`、`glossaries.py:27-28`、`nomencl.py:17-18` 各一份。
- 处理块：`makeindex.py:188-213`、`glossaries.py:152-209`、`nomencl.py:80-110` 高度重复。
- `GlossariesParser` 缺少 makeindex 的续行处理（见上表）。

**建议**：抽 `parsers/index_common.py`（或复用现有 `xindy_patterns.py` 的方式），统一正则、待处理状态、样式错误续行；各 parser 只保留差异字段。

### 3.3 xindy 两份

- `parsers/xindy.py:36-90` 与 `glossaries.py:216-250 _parse_xindy` 基本同构但语义不同：前者只入 stats，后者计 warnings/entries。
- `xindy.py` 覆盖率仅 15%，两份实现都没有共享测试矩阵。

**建议**：合并为一个基础扫描器，调用方通过 flags 决定是否计 entries/warnings；用同一组 `.glg` fixtures 验证。

### 3.4 统计重算四份、完整度不一

| 位置 | 重算字段 |
|---|---|
| `core/engine.py:59-91` | levels/errors/warnings/overfull/underfull/undefined（最完整） |
| `exporters/json_exporter.py:244-251` | 仅 error/warning/entries_count |
| `exporters/json_exporter.py:218-225` | 仅 entries_count |
| `cli/main.py:271-274` | 仅 error/warning/entries_count |

这是 B1 的结构性根因。**建议**：单一 `recompute_stats(entries, base_stats)`，所有过滤路径调用；保留旧键但必须重算或删除。

### 3.5 展示层平行映射

- `display/formatter.py` 的 `_LEVEL_ORDER/_LEVEL_TITLE/_LEVEL_SYMBOL_MARKUP/_LEVEL_SEP_STYLE` 四张表；
- `display/printer.py:38-47` 的 `_LEVEL_LOGGER` 第五张表；
- `display/printer.py:18-33` 既 `import formatter as _formatter` 又逐个导入其私有名。

**建议**：合并为一个 `LevelStyle` 数据类/字典，避免新增等级时漏改。

### 3.6 无 rich 回退控制台两份

- `display/printer.py:53-67`
- `tools/utils.py:42-61`

两处都做 markup 剥离、`status` 空上下文；逻辑重复且都每次编译正则。**建议**：抽 `display/console.py` 的 `FallbackConsole`，两处共用。

## 4. 性能分析与优化候选

> 以下均为 `TEST_OBSERVATION`：单机、单轮或单对样本，未做多轮重复、mutant、生产 profile。按性能 Skill 口径，**不能据此签发生产收益**，只能作为优化候选与回归基线。

### 4.1 现有性能门禁

| 场景 | 本轮观测 | 阈值 | 余量 |
|---|---|---|---|
| 100k 行解析 | 300.26ms（前一轮 406.15ms） | 500ms | 约 19%–40%，随机器噪声波动 |
| 解析 + hint（100k 行，40001 entries） | parse 357.79ms + hint 460.26ms = 818.05ms | 2s | 约 59% |
| 缺字形 5000 条 | 48.82ms | — | — |
| 畸形长行 5k/31k | 0.790ms / 6.727ms | — | — |
| BibTeX 15000 帧 | 74.37ms | — | — |
| BibTeX 200→2000 帧 | 2.31ms→19.42ms，ratio 8.41 | 线性检查 | 通过 |

100k 解析余量不算宽裕，CI 机器抖动时可能逼近 500ms；建议把门禁改成相对基线或放宽到 600ms，但这是测试稳定性问题，不是解析器退化。

### 4.2 cProfile 热点（97,999 行、21,000 entries）

| 热点 | 累计时间 | 说明 |
|---|---|---|
| `parse` | 0.858s | 总解析 |
| `re.Pattern.match` | 1,651,992 次 / 0.284s | 每行多次正则匹配 |
| `_parse_line` | 0.235s | 行级状态机 |
| `_parse_file_stack` | 0.128s | 逐字符扫描括号栈 |
| `_match_bad_box` | 0.109s | 每条候选都跑多组正则 |
| `_parse_bad_box` | 0.111s | 同上 |
| `print_summary` | 0.638s | 其中 `_format_entry` 0.545s |

`_format_entry` 慢在每条 entry 都做 `Path.cwd()` / `relative_to`；对同一文件重复计算。

### 4.3 同输入 A/B（单对样本，未实施到仓库）

| 候选 | 改前 | 改后 | 变化 | 输出一致性 |
|---|---|---|---|---|
| `_parse_file_stack` 先判 `"(" not in line and ")" not in line` 直接返回 | 241.3ms | 224.4ms | −16.9ms（约 7%） | 同输入结果一致 |
| `_format_entry` 按文件缓存相对路径 | 162.9ms | 28.1ms | −134.8ms（约 83%） | 逐字节相同 |

第一项收益有限，第二项收益大但属于展示层；两者都应在正确性修复之后、带 golden 输出与 benchmark 再落地。

### 4.4 结构型低效

- `core/engine.py:242` 与 `254` 对同一 step 实例化 parser 两次：第一次只为 `_read_log_text`，其 `_resolved_paths` 缓存被丢弃，第二次重新解析。
- `core/engine.py:132-133` 默认 `print_terminal=True` 且 `summary_max_entries=None`；库用户直接 `run_pipeline` 大日志会打印数万行。CLI 才默认 10 条。
- `ref_tracker.detect_mode()` 在 `engine.py:296` 与 `extract_current_with_counts` 内部各调一次。
- `state.save_cache` 每次构建都 fsync 一次，即使引用集合未变。
- `display/printer.py:9-14` 模块级急切 import `rich`；`engine.py:14` 又模块级 import printer，导致 `import pytexlogs` 即使不用摘要也加载 rich。A/B：常规 91.7ms，屏蔽 rich 77.2ms（约 16% 启动开销）；`pytexlogs --version` 冷启动 PowerShell 计时 248ms。

### 4.5 启动与打包

- `import pytexlogs` 91.7ms；屏蔽 rich 77.2ms。
- wheel 安装独立目录后导入正常，`py.typed`、`entry_points.txt` 均正确；`uv build` 无打包错误。
- 结论：启动开销主要来自可选 rich 的急切导入，可用惰性导入解决，但需保证 `rich` 缺失时回退路径仍可用。
